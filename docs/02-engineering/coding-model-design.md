# Forge H2 Enterprise 코딩 모델 설계

## 목표

Forge H2 Enterprise는 단순히 코드를 생성하는 모델이 아니라, 프로젝트를 읽고 계획을 세우며 변경을 검증하는 코딩 에이전트를 목표로 한다.

## 전체 구조

```text
사용자 요청
  ↓
의도·위험도 분류
  ↓
프로젝트 컨텍스트 검색
  ↓
계획 생성
  ↓
코드 생성 또는 수정
  ↓
diff 검토
  ↓
테스트 실행
  ↓
실패 원인 분석 및 수정 제안
```

## 모델 구성

### 1. 기본 모델

초기에는 DeepSeek-Coder, Qwen-Coder 계열처럼 이미 학습된 코드 모델을 사용한다. 개인 PC에서 처음부터 수십억 파라미터 모델을 학습하는 것은 비용과 데이터 측면에서 비현실적이다.

### 2. 컨텍스트 계층

- 현재 파일과 관련 파일
- `README.md`, 프로젝트 설정, 테스트
- 최근 변경 diff
- 프로젝트 지침(`project.json`)
- 오류 로그와 실행 결과

모델 입력은 전체 저장소가 아니라 관련 파일을 검색해 구성한다.

### 3. 도구 계층

모델이 직접 임의 명령을 실행하지 않고 다음 도구를 제한적으로 호출한다.

- `list_files`
- `read_file`
- `search_code`
- `propose_patch`
- `run_tests`
- `get_test_output`

파일 수정과 명령 실행은 항상 사용자 승인 후 수행한다.

## 학습 전략

### 1단계: 프롬프트 기반 MVP

로컬 모델에 시스템 지침과 프로젝트 컨텍스트를 전달한다. 학습 없이 바로 검증할 수 있다.

### 2단계: LoRA/QLoRA

다음 예시를 모아 소형 어댑터를 학습한다.

- 나쁜 코드 → 개선 코드
- 오류 로그 → 원인과 수정
- 요구사항 → 계획과 파일 목록
- 테스트 실패 → 수정 patch

### 3단계: 선호도 학습

두 답변 중 더 안전하고 테스트 가능한 답변을 선택해 품질 기준을 학습한다.

## 데이터 형식

```json
{
  "instruction": "로그인 API에 입력 검증을 추가해줘",
  "context": "관련 파일과 테스트 내용",
  "response": "변경 계획, diff, 테스트 명령",
  "quality": {"tests_pass": true, "minimal_diff": true, "安全": true}
}
```

## 평가 지표

- 테스트 통과율
- 올바른 파일 선택률
- 불필요한 변경 비율
- 보안 취약점 발생률
- 첫 답변 해결률
- 사용자 승인 없이 변경한 횟수: 항상 0

## Forge H2 Enterprise 구현 순서

1. Ollama 또는 API 기반 실제 코딩 모델 연결
2. 프로젝트 파일 검색을 모델 입력에 포함
3. 계획·diff·테스트 형식 강제
4. 테스트 실행 도구 추가
5. 사용자 승인 후 patch 적용
6. 자체 코딩 데이터셋으로 LoRA 학습

## 핵심 원칙

Forge H2 Enterprise의 경쟁력은 모델 크기보다 **프로젝트 맥락을 정확히 읽고, 작은 변경을 제안하며, 테스트로 검증하는 작업 루프**에 둔다.
