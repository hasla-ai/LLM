## F-01 (중대) 단계 분류가 세 파일에서 서로 다르다

미션 20개가 잘못된 전문가 Agent 에게 라우팅된다.

### 관측

`docs/03-governance/mission-catalog.md` 의 단계 구분:

| 미션 | 카탈로그 단계 |
|---|---|
| M-021 ~ M-030 | 입지·토지·GIS |
| M-031 ~ M-040 | 수소 생산·공급·저장 |
| M-041 ~ M-050 | 발전기·열·전력계통 |
| M-051 ~ M-060 | 개념설계 |

`workflow/process-agent-map.json` 의 단계 구분:

| phase | 이름 | 미션 |
|---|---|---|
| P03 | site | M-021 ~ M-040 |
| P04 | hydrogen | M-041 ~ M-050 |
| P05 | power_grid | M-051 ~ M-060 |

즉 `M-041 select_power_technology` 는 카탈로그상 발전 미션인데 workflow 맵에서는
**수소 단계**의 리드 Agent 에게 배정된다. `M-051 freeze_design_basis` 는 개념설계
미션인데 **계통 단계**로 간다. M-041 ~ M-060 의 20개가 전부 한 칸씩 밀려 있다.

여기에 `schemas/mission-definition.schema.json` 의 `phase` enum 은

```
intake | business | site | hydrogen | power_grid | concept_design |
safety_permit | feed_epc | construction | operations
```

로 `concept_design` 을 갖고 `commissioning` 이 없다. workflow 맵은 정반대로
`commissioning` 이 있고 `concept_design` 이 없다. 세 파일이 전부 다르다.

### 영향

- Agent 호출·회의 소집·승인 역할이 20개 미션에서 잘못 결정된다.
- `mission-definition.schema.json` 을 만족하는 미션 정의를 쓸 수 없다.
  어떤 phase 값을 넣어도 세 문서 중 둘과 어긋난다.

### 조치

카탈로그와 workflow 맵 중 어느 쪽을 정본으로 할지 먼저 결정한다.
그 뒤에 나머지 두 파일과 schema enum 을 맞춘다. 이것이 미션 속성 이식의 선행조건이다.

## F-02 (중대) 미션 카탈로그가 자기 스키마를 만족하지 않는다

`schemas/mission-definition.schema.json` 은 다음을 **필수**로 요구한다.

- `dependencies`
- `completion_criteria`
- `block_conditions`
- `input_contract.required_fields` / `units_required`
- `output_contract.quality_checks`
- `review_policy`

`mission-catalog.md` 의 100행 표에는 이 중 어느 것도 없다. 함수명·입력·출력·담당·Gate
만 있다. 스키마는 정의됐지만 그것을 만족하는 미션 정의가 하나도 없다.

참고 자료로 `docs/03-governance/mission-library-100.json` 을 추가했다. 선행관계 DAG,
완료 판정기준, 차단조건 후보, 기간이 100개 전건에 채워져 있다. 다만 ID 체계(M001 vs
M-001)와 게이트 수(G0~G9 vs G0~G7)가 달라 그대로 병합할 수 없다. F-01 해소 후
매핑 테이블이 필요하다.

## F-03 (중대) `app/main.py` 의 계산이 거버넌스를 따르지 않는다

`/api/mvp/feasibility` 의 결함.

### F-03a 상수가 코드에 박혀 있다

```python
h2_kwh_per_kg = 33.33
```

`knowledge/formula-library.json` 이 존재하고 `requires_unit_check: true` 까지 선언돼
있는데 앱은 라이브러리를 참조하지 않는다. 정확값은 33.322 kWh/kg (119.96 MJ/kg) 이며
수치 오차 자체는 0.02% 로 무의미하다. 문제는 **출처 없는 상수가 코드에 사는 것**이다.

### F-03b 총발전단과 순출력이 구분되지 않는다

`power_mw` 가 어느 쪽인지 정의가 없고 소내부하가 모델에 없다. 순출력을 입력하면
실제 필요 수소량이 소내부하율(통상 5~12%)만큼 과소산정된다. 공급계약 물량과 저장
설비가 이 값에서 나온다.

### F-03c 저장 산정에 사용가능 잔압이 빠져 있다

```python
storage_kg = h2_kg_per_hour * 24 * payload.storage_days
```

압축가스는 최소사용압력 아래를 인출할 수 없다. 설치 저장량은 이 값을 사용가능
비율(통상 0.7~0.85)로 나눈 것이어야 한다. 빠지면 저장설비가 15~30% 과소산정된다.

### F-03d 저장밀도 기본값의 근거가 없다

`storage_density_kg_m3 = 30.0` 은 대략 450~500 bar 에 해당한다. 200 bar / 288 K /
Z=1.10 에서 수소 밀도는 약 **15.3 kg/m³** 다. 밀도가 2배 틀리면 저장 용적이 2배
틀리고, `storage_volume_m3 * 3.0` 을 타고 부지면적까지 틀어진다.

### 조치

`app/calc.py` 를 추가했다. 네 결함을 모두 고쳤고 모든 결과에 공식 ID·가정·근거등급이
붙는다. `app/main.py` 가 이 모듈을 호출하도록 교체하는 것은 별도 작업으로 둔다
(기존 API 응답 형태가 바뀌므로 검토가 필요하다).

## F-04 (보통) 공식 라이브러리에 수소 고유식이 없었다

`knowledge/formula-library.json` 의 15개는 옴의 법칙·베르누이·훅의 법칙 같은 일반
공학 기초식이며, 수소발전 플랜트 고유식은 하나도 없었다.

`knowledge/formula-library-h2.json` 을 추가했다. 18식, 검증 케이스 22개, 전부
`machine_checked`. 자격자·발행기관 확인 전이므로 `expert_verified` 로 올리지 않았다.

## F-05 (보통) 레포에 테스트가 없다

기존 15개 공식 중 **14개에 `validation_cases` 가 없다.** CI 도 테스트 파일도 없다.

`tools/validate_formulas.py` 를 추가했다. 공식 검증 케이스를 실제로 실행하고,
레포 스키마로 인스턴스 문서를 검증한다. 현재 결과:

```
검증 케이스 통과 23 · 실패 0 · 경고 14
스키마 통과 6 · 실패 0
```

경고 14건은 전부 기존 라이브러리의 검증 케이스 누락이다.

## F-06 (경미) 스키마를 검증할 수 있는 도구가 없었다

`schemas/*.schema.json` 은 `$id` 가 `https://forge-h2.local/...` 절대 URL 이고
`$ref` 는 상대 경로다. 로컬 레지스트리 없이는 해석되지 않아 검증 시도 자체가
네트워크 요청으로 빠진다. `tools/validate_formulas.py` 가 로컬 레지스트리를 구성한다.
