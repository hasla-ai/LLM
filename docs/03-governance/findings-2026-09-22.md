## F-01 (중대·해소됨) 단계 분류가 세 파일에서 서로 다르다

미션 20개가 잘못된 전문가 Agent 에게 라우팅된다.

### 관측

`docs/03-governance/mission-catalog.md` 의 단계 구분:

| 미션 | 카탈로그 단계 |
|---|---|
| M-021 ~ M-030 | 입지·토지·GIS |
| M-031 ~ M-040 | 수소 생산·공급·저장 |
| M-041 ~ M-050 | 발전기·열·전력계통 |
| M-051 ~ M-060 | 개념설계 |

`workflow/process-agent-map.json` 의 단계 구분:

| phase | 이름 | 미션 |
|---|---|---|
| P03 | site | M-021 ~ M-040 |
| P04 | hydrogen | M-041 ~ M-050 |
| P05 | power_grid | M-051 ~ M-060 |

즉 `M-041 select_power_technology` 는 카탈로그상 발전 미션인데 workflow 맵에서는
**수소 단계**의 리드 Agent 에게 배정된다. `M-051 freeze_design_basis` 는 개념설계
미션인데 **계통 단계**로 간다. M-041 ~ M-060 의 20개가 전부 한 칸씩 밀려 있다.

여기에 `schemas/mission-definition.schema.json` 의 `phase` enum 은

```
intake | business | site | hydrogen | power_grid | concept_design |
safety_permit | feed_epc | construction | operations
```

로 `concept_design` 을 갖고 `commissioning` 이 없다. workflow 맵은 정반대로
`commissioning` 이 있고 `concept_design` 이 없다. 세 파일이 전부 다르다.

### 영향

- Agent 호출·회의 소집·승인 역할이 20개 미션에서 잘못 결정된다.
- `mission-definition.schema.json` 을 만족하는 미션 정의를 쓸 수 없다.
  어떤 phase 값을 넣어도 세 문서 중 둘과 어긋난다.

### 조치 — 완료 (2026-09-23)

`mission-catalog.md` 를 정본으로 채택했다 (D-024). 카탈로그만이 100개 미션 전건의
ID·함수·입력·출력·담당·Gate 를 한 표에 갖고 있어 다른 두 파일을 카탈로그에서 파생할 수
있다. 역방향은 불가능하다.

`schemas/mission-definition.schema.json` 의 phase enum 은 **변경하지 않았다.** 검사 결과
enum 10개가 이미 카탈로그의 10단계와 이름·순서가 일치했다. 어긋나 있던 것은 workflow
맵뿐이었다.

`workflow/process-agent-map.json` 을 v1.1.0 으로 재작성했다.

- 10개 단계 전부를 카탈로그의 10미션 블록에 맞췄다. 실제 드리프트는 이 문서가 처음
  기록한 M-041~M-060 보다 넓었다. P01/P02 경계가 M-006 에서, P03 이 site 와 hydrogen
  20개를 한 단계로 삼키는 지점에서도 어긋나 있었다.
- 카탈로그에 없는 `commissioning` 단계를 제거하고, 리드 Agent·필수 Agent·산출물·차단조건을
  `construction` 으로 흡수했다. 카탈로그 Phase 8 이 M-087~M-089 시운전 미션(G6)을
  포함하기 때문이다.
- `concept_design` 단계(P06, M-051~M-060, G3)를 신설했다.
- 카탈로그는 미션별 Gate 를 주고 Phase 8 은 G5/G6/G7 에 걸친다. 단일 `gate_id` 로
  표현할 수 없어 `gate_ids` 와 `mission_gates` 를 추가했다.
- `international_overlay_phase_controls` 를 이름 기준으로 재매핑했다.

### 회귀 방지

`tools/check_phase_alignment.py` 가 세 파일의 일치를 검사한다. 정본 자체의 무결성(미션
100개 연속·중복 없음·단계별 연속 블록)도 함께 본다.

```
python tools/check_phase_alignment.py
```

수정 전 HEAD 기준 불일치 35건을 검출하고, 수정 후 0건으로 통과한다. 미션 한 칸 밀기·단계
이름 훼손·복수 Gate 정보 삭제·enum 값 교체·정본 미션 삭제 5개 변조를 주입해 전부
탐지되는 것을 확인했다.

## F-02 (중대) 미션 카탈로그가 자기 스키마를 만족하지 않는다

`schemas/mission-definition.schema.json` 은 다음을 **필수**로 요구한다.

- `dependencies`
- `completion_criteria`
- `block_conditions`
- `input_contract.required_fields` / `units_required`
- `output_contract.quality_checks`
- `review_policy`

`mission-catalog.md` 의 100행 표에는 이 중 어느 것도 없다. 함수명·입력·출력·담당·Gate
만 있다. 스키마는 정의됐지만 그것을 만족하는 미션 정의가 하나도 없다.

### mission-library-100.json 은 이식 원본이 될 수 없다 (2026-09-23 정정)

이 문서는 당초 `mission-library-100.json` 의 선행관계·완료기준·차단조건을 카탈로그로
이식하면 된다고 적었다. **그 전제가 틀렸다.** ID 체계와 게이트 수 차이는 표면적인
문제였고, 실제로는 두 문서가 서로 다른 100개 미션 분해다.

| 비교 | 결과 |
|---|---|
| 위치 대응(M-0NN ↔ M0NN)에서 산출물 엔티티가 일치 | **2 / 100** |
| 라이브러리 전체에서 대응 미션을 찾을 수 있음 | **3 / 100** |

단계 구성 자체가 다르다. 라이브러리는 단계마다 게이트가 하나씩 붙은 G0~G9 이고
상업운전(COD)에서 끝난다. 카탈로그는 게이트가 단계를 가로지르는 G0~G7 이고 운영·정비
단계를 더 갖는다. 라이브러리 P5 `설계기준·FEED` 는 카탈로그에서 Phase 5 개념설계와
Phase 7 FEED·EPC 로 쪼개지고, 라이브러리 P6 안전성·P7 인허가는 카탈로그 Phase 6 하나로
합쳐진다. 카탈로그 Phase 9(운영)에 대응하는 라이브러리 단계는 없다.

ID 를 맞춰 병합하면 97개 미션에 **틀린 선행관계·완료기준·차단조건이 들어간다.**
매핑 테이블을 만들 대상이 사실상 없다. 라이브러리는 참고 자료로만 남긴다 (D-025).

### 카탈로그만으로 채울 수 있는 범위 (2026-09-23 측정)

`tools/build_mission_definitions.py` 가 정본에서 도출 가능한 것과 아닌 것을 나눈다.

| 필드 | 상태 |
|---|---|
| `mission_id` · `code` · `phase` · `owner_role` · `gate` | 카탈로그에서 직접 도출 |
| `output_contract.required_fields` | 카탈로그 출력 칸에서 도출 |
| `risk_class` · `review_policy` · `executor` | 규칙으로 제안, **확인 필요** |
| `purpose` · `completion_criteria` · `block_conditions` · `quality_checks` · `schema_ref` | **자격자 작성 필요** |

`dependencies` 는 산출물→입력 사슬로 도출을 시도했다.

| 입력 토큰 235건 | |
|---|---|
| 정확 일치 | 18 |
| 부분일치 유일 → 선행관계 확정 | 55 |
| 부분일치 모호 → **확정 불가** | 29 |
| 산출 미션 없음 (외부 입력·비엔티티) | 133 |

확정한 선행관계는 73건(51개 미션)이다. 모호한 29건은 카탈로그의 입력 칸이 약어라서
생긴다. 예를 들어 M-003 의 입력 `Intent` 는 M-001 의 `ProjectIntent` 인지 M-002 의
`NormalizedIntent` 인지 카탈로그만으로 결정되지 않는다. 추측하면 미션 라우팅에 틀린
선행관계가 들어가므로 확정하지 않고 `extensions.dependency_derivation.ambiguous_inputs`
에 후보와 함께 남겼다.

### 현재 상태

`docs/03-governance/mission-definitions.draft.json` — 100건, 스키마 적합 100/100,
**내용 완결 0/100**.

```
python tools/build_mission_definitions.py   # 정본에서 골격 생성
python tools/check_mission_definitions.py   # 스키마 적합·내용 완결·정본 정합성
```

검사기는 스키마 적합과 내용 완결을 **따로 센다.** 자리표시자(`TODO-AUTHOR`)로 채운
골격도 스키마는 통과하기 때문이다. 둘을 한 숫자로 합치면 골격이 완성본으로 오인된다.

F-02 는 미해소다. 남은 일은 기계가 할 수 없다. 100개 미션의 목적·완료 판정기준·차단조건을
자격자가 작성해야 하고, 모호한 선행관계 29건을 결정해야 한다.

## F-03 (중대) `app/main.py` 의 계산이 거버넌스를 따르지 않는다

`/api/mvp/feasibility` 의 결함.

### F-03a 상수가 코드에 박혀 있다

```python
h2_kwh_per_kg = 33.33
```

`knowledge/formula-library.json` 이 존재하고 `requires_unit_check: true` 까지 선언돼
있는데 앱은 라이브러리를 참조하지 않는다. 정확값은 33.322 kWh/kg (119.96 MJ/kg) 이며
수치 오차 자체는 0.02% 로 무의미하다. 문제는 **출처 없는 상수가 코드에 사는 것**이다.

### F-03b 총발전단과 순출력이 구분되지 않는다

`power_mw` 가 어느 쪽인지 정의가 없고 소내부하가 모델에 없다. 순출력을 입력하면
실제 필요 수소량이 소내부하율(통상 5~12%)만큼 과소산정된다. 공급계약 물량과 저장
설비가 이 값에서 나온다.

### F-03c 저장 산정에 사용가능 잔압이 빠져 있다

```python
storage_kg = h2_kg_per_hour * 24 * payload.storage_days
```

압축가스는 최소사용압력 아래를 인출할 수 없다. 설치 저장량은 이 값을 사용가능
비율(통상 0.7~0.85)로 나눈 것이어야 한다. 빠지면 저장설비가 15~30% 과소산정된다.

### F-03d 저장밀도 기본값의 근거가 없다

`storage_density_kg_m3 = 30.0` 은 대략 450~500 bar 에 해당한다. 200 bar / 288 K /
Z=1.10 에서 수소 밀도는 약 **15.3 kg/m³** 다. 밀도가 2배 틀리면 저장 용적이 2배
틀리고, `storage_volume_m3 * 3.0` 을 타고 부지면적까지 틀어진다.

### 조치

`app/calc.py` 를 추가했다. 네 결함을 모두 고쳤고 모든 결과에 공식 ID·가정·근거등급이
붙는다. `app/main.py` 가 이 모듈을 호출하도록 교체하는 것은 별도 작업으로 둔다
(기존 API 응답 형태가 바뀌므로 검토가 필요하다).
